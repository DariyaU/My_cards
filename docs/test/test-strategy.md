## 1. Введение

### 1.1. Цель документа
Определить стратегию, уровни, подходы и инструменты тестирования приложения Flashcards (MVP).

### 1.2. Область применения
Документ охватывает все виды тестирования: функциональное, UI/UX, производительность, совместимость, локализацию.

---

## 2. Уровни тестирования

### 2.1. Unit-тестирование (Модульное)
**Что тестируем:**
- Модели данных (Deck, Card)
- Бизнес-логика (подсчет статистики, фильтрация карточек)
- Функции экспорта/импорта JSON
- Валидация полей

**Инструменты:** 
- `flutter_test` (встроенный фреймворк)
- `mockito` для мокирования зависимостей

**Критерий покрытия:** ≥ 80% строк бизнес-логики

**Ответственный:** Разработчик

---

### 2.2. Integration-тестирование (Интеграционное)
**Что тестируем:**
- Взаимодействие UI с локальным хранилищем (Hive/SQLite)
- Сохранение/загрузка данных после перезапуска приложения
- Работа с файловой системой (экспорт/импорт)

**Инструменты:**
- `flutter_test` + `integration_test`
- Тестовые данные в изолированном хранилище

**Критерий покрытия:** Все критические пути работы с данными

**Ответственный:** Разработчик + QA

---

### 2.3. UI/E2E-тестирование (Сквозное)
**Что тестируем:**
- Ключевые пользовательские сценарии (создание набора → добавление карточек → изучение)
- Навигация между экранами
- Локализация (переключение RU/EN)

**Инструменты:**
- `integration_test` (Flutter)
- Эмулятор Android / Реальное устройство

**Критерий покрытия:** Все User Story MVP

**Ответственный:** QA

---

### 2.4. Ручное тестирование
**Что тестируем:**
- Визуальная проверка UI (соответствие wireframes)
- Юзабилити (удобство использования)
- Доступность (скринридеры, контрастность)
- Локализация (качество перевода, переносы строк)

**Методы:**
- Smoke-тестирование (перед каждым релизом)
- Regression-тестирование (после каждой итерации)
- Exploratory testing (исследовательское тестирование)

**Ответственный:** QA + Product Owner

---

### 2.5. Тестирование производительности
**Что тестируем:**
- Время запуска приложения (< 2 сек)
- Время отклика UI (< 100 мс)
- Работа со списком из 1000+ карточек (без лагов)

**Инструменты:**
- Flutter DevTools (Performance tab)
- Логирование времени выполнения операций

**Критерии:**
- NFR-01 (Производительность) выполнен полностью

**Ответственный:** Разработчик + QA

---

### 2.6. Тестирование совместимости
**Что тестируем:**
- Поддержка версий Android 8.0–14 (API 26–34)
- Разные размеры экранов (телефон, планшет)
- Разрешения экрана (HD, Full HD, 2K)

**Инструменты:**
- Android Emulator (разные конфигурации)
- Firebase Test Lab (опционально)
- Реальные устройства (при наличии)

**Ответственный:** QA

---

### 2.7. Тестирование локализации (i18n/l10n)
**Что тестируем:**
- Корректность перевода всех строк (RU/EN)
- Переключение языка без перезапуска
- Сохранение выбора языка
- Длина строк (нет ли обрезания текста)

**Ответственный:** QA + Native speakers (при наличии)

---

### 2.8. Security-тестирование (Базовое)
**Что тестируем:**
- Отсутствие чувствительных данных в логах
- Нет хардкода секретов в коде
- Проверка разрешений (только необходимые)

**Инструменты:**
- Статический анализ кода (dart analyze)
- Ручная проверка

**Ответственный:** Разработчик

---

## 3. Что НЕ тестируем (Out of Scope)

- Нагрузочное тестирование сервера (сервер отсутствует)
- Тестирование безопасности API (API отсутствует)
- Кросс-браузерное тестирование (веб-версии нет в MVP)
- Тестирование интеграции со сторонними сервисами (интеграций нет)

---

## 4. Критерии качества (Definition of Done для тестирования)

Задача/User Story считается протестированной, если:

✅ Все автотесты (unit + integration) написаны и проходят  
✅ Ручные тест-кейсы выполнены, статус = Pass  
✅ Нет открытых багов критичности S1 (Critical) и S2 (Major)  
✅ Код покрыт тестами ≥ 80% (для бизнес-логики)  
✅ Документация обновлена (traceability.md, test reports)

---

## 5. Типы дефектов и приоритеты

| Серьезность | Описание | Пример | Срок исправления |
|-------------|----------|--------|------------------|
| **S1 — Critical** | Приложение падает, данные теряются, критическая функция не работает | Падение при запуске, потеря всех наборов | Немедленно |
| **S2 — Major** | Основная функция работает некорректно, есть обходной путь | Не сохраняется статус карточки, но можно перезапустить сессию | До следующего релиза |
| **S3 — Minor** | Косметические ошибки, опечатки, неудобный UI | Неправильный цвет кнопки, опечатка в тексте | По возможности |
| **S4 — Trivial** | Пожелания по улучшению, не влияющие на функционал | "Хотелось бы анимацию..." | В бэклог |

## 6. Инструменты тестирования

| Категория | Инструмент | Назначение |
|-----------|------------|------------|
| Unit-тесты | `flutter_test`, `mockito` | Тестирование логики |
| Integration-тесты | `integration_test` | E2E сценарии |
| Статический анализ | `dart analyze`, `flutter lint` | Поиск ошибок в коде |
| Форматирование | `dart format` | Единый стиль кода |
| Покрытие кода | `genhtml`, `lcov` | Отчеты о покрытии |
| Эмуляторы | Android Studio Emulator | Тестирование на разных версиях Android |
| Управление тестами | GitHub Issues + Markdown | Хранение тест-кейсов и баг-репортов |

## 7. Процессы

### 7.1. Процесс обнаружения бага
1. Тестировщик находит дефект
2. Заводится Issue в GitHub с меткой `bug`
3. Заполняется шаблон баг-репорта (см. `bug-report-template.md`)
4. Присваивается серьезность (S1–S4) и приоритет (P0–P3)
5. Разработчик исправляет, тестировщик проверяет фикс

### 7.2. Процесс регрессионного тестирования
Перед каждым релизом:
1. Прогоняется полный набор regression-чеклистов
2. Проверяются все закрытые баги (fix verification)
3. Обновляется отчет о тестировании (`test-reports/`)

---

## 8. Метрики тестирования

| Метрика | Целевое значение | Как измеряем |
|---------|------------------|--------------|
| Покрытие кода тестами | ≥ 80% | `lcov` отчет |
| Процент пройденных тест-кейсов | ≥ 95% | Test execution report |
| Количество открытых багов S1/S2 | 0 | GitHub Issues |
| Время на тестирование одной US | ≤ 4 часов | Time tracking |

---

## 9. Риски тестирования

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Недостаток реальных устройств для тестирования | Высокая | Среднее | Использовать эмуляторы + Firebase Test Lab |
| Изменение требований в процессе разработки | Средняя | Высокое | Гибкий подход, обновление тест-кейсов |
| Недостаток времени на тестирование | Средняя | Высокое | Приоритизация тестов (Smoke → Regression) |
